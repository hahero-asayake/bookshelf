# #402 step3: 本棚一覧の仮想化（設計案の比較・tp）

## ハヘロ向け要約（方針だけ）

本棚一覧を「画面に見えている付近の本だけを置く」方式に変えると、並べ替えの固まりと、冊数が増えた時のスクロールのカクつきが解消する見込みです。決めてほしいのは次の2点です。
1. **この方式に進めてよいか。** 代わりに、ブラウザのページ内検索（Ctrl+F）と印刷では、画面の付近の本しか対象にならなくなります。アプリ内の検索（⌘K・絞り込み）は今のままです。
2. **古い見た目プラグインを使っている間は、今の方式（遅いまま）に自動で戻す、でよいか。** 対象は、横スクロールや多段組で一覧の形を丸ごと変えるもので、今は実際には動いていません。

（技術的な細目は②が推奨どおりに決め、結果だけ伝えます）

## 1. 案

### A. 行単位の窓（推奨）

- 並び順の配列（`displayOrder`）を正本にし、DOM には「可視行 ± overscan 行」だけを置く。
- **列数・行高**は `ResizeObserver`（`#bookshelf` の幅、それと1枚目のカードの高さ）で追う。表紙サイズ（S/M/L）の変更・画面回転・ペインの開閉でも計算し直す。
- **上下の余白**は `#bookshelf` の `padding-top/bottom` で作る（step2 契約1＝子は `.book-item` だけ）。
- **overscan**: 下に約1200px（≒4行）、上に約2行。#389 の先読みの rootMargin（300px 0 1200px 0）と揃え、窓に入る前に表紙の読み込みが始まるようにする。
- **窓の開始位置**は lcm(12, 列数) の倍数に切り捨てる（step2 契約5）。
- **更新のきっかけ**: スクロールの `scroll` イベントを rAF で1フレーム1回にまとめる。範囲が変わった時だけ、差分（抜けた分を外し、入った分を足す）で付け外しする。
- **カードの再利用**: asin → 要素の Map（キャッシュ）を持ち、範囲に戻ったカードは作り直さずに付け直す。`book:updated` 等で、その asin だけ捨てる。
- **並べ替えの時**: `displayOrder` を作り直し、今のスクロール位置の窓だけを描く。913冊でも3000冊でも DOM の操作は20〜40件で済む。

### B. 窓と content-visibility の併用

- A と同じ窓で、overscan を広く取る（上下とも2画面ぶん）。窓の中のカードには、今の `content-visibility:auto` を残す。
- 良い点: 付け外しの回数が減る（範囲が変わりにくい）。速いフリックでも、DOM にあるカードが多いので白抜けしにくい。
- 悪い点:
  - DOM 件数が A の3〜4倍（60〜120件）。
  - cv:auto のまわりの既知の罠を抱えたまま。IntersectionObserver が交差しない（#389）、WebKit のペイント欠落（#371/#373）。
  - step1 の窓試作は、窓の中を `content-visibility: visible` にして測っているので、B の値は**実測していない**。

### C. IntersectionObserver の番兵で段階的にマウント

- 最初に1画面ぶんだけ置き、末尾の番兵（空の要素）が rootMargin に入ったら、次の1塊（例: 30件）を足す。
- **外さない版（C1）**: 並べ替え直後は速い。ただしスクロールするほど DOM が増え、最後には全件 DOM に戻る。3000冊のスクロールのカクつきは直らない。
- **上側も外す版（C2）**: 番兵を上下に置く。実質は A と同じことを非同期の通知で行うことになる。
  - IO の通知は1フレーム遅れて届く＝速いスクロールで白抜けしやすい。
  - 番兵は `#bookshelf` の子になる＝step2 契約1（子は `.book-item` だけ）に反する。
  - 戻る・進むで深い位置へ一気に飛ぶ時、そこまで順に足す必要がある。

### （参考）D. #401 案C＝並べ替えの時だけ段階描画（ADR-139 の推奨）

- 可視範囲を先に描き、残りは空き時間に小分けで足す。描き終われば今と同じ全件 DOM。
- 契約を変えずに「固まる時間」を縮められる。ただし描き終わった後は全件 DOM なので、**3000冊のスクロール（step1: 50ms超が65〜80件）は直らない**。

## 4. kill-switch・影モード・段階分け

- **kill-switch**: `window.BOOKSHELF_LIST_VIRTUAL`（既定 OFF）と `localStorage['bookshelf:list-virtual']`（実機で切り替えられるように）。OFF の時は、今の全件 DOM の経路を**そのまま**通る。ON でも、次の場合は全件 DOM に落とす。
  - 全件DOMの要求（契約4）がある
  - 冊数がしきい値未満
  - 影の自己検査で食い違いが出た（その場で全件 DOM に戻し、console に記録する）
- **影モード**（step4・OFF の間）: 全件 DOM で描いた後、窓の計算（開始・終了 index・余白の高さ）だけを並走させる。次の2点を毎回突き合わせる。
  - 実 DOM の並び（`data-asin` の列）と `displayOrder.slice(start,end)`
  - 計算した行の top と、実カードの `offsetTop`
  - ずれは console と `window.__listVirtualShadow` に数える（#359/#371 の影の自己検査と同じ型）。
- **段階分け**:
  - 4a: 窓の計算（範囲・開始位置の揃え・座標→index）を純関数にして、単体テスト
  - 4b: 窓の描画を flag OFF で入れ、影モードを有効にする。既存 E2E は全部緑のまま
  - 4c: 統合点（ドラッグの固定と index でのドロップ・先読みの observe・読み済み集合・NavState の順序・選択）と、その E2E。ドラッグは WebKit のタッチ型（#337 の型）で
  - 4d: プラグイン契約（範囲イベント・全件DOMの要求・`getDisplayedBooks`・`data-index`）と、view-spines を有効にした E2E（色・背の高さの一致・全件DOMへ戻ること）
  - 5: 913冊・3000冊で前後計測（並べ替え3操作・スクロール・空き表示）、WebKit 390・chromium x4。実機の画面録画は人間に依頼。既定 ON にするかは tp で決める
- **#401 との関係**: 推奨は A。#401 の案C（D）は、A の kill-switch OFF 時の改善としては残せる。ただし同じ `_renderListDiff`・`updateDisplay` を触るため、step4 の前に②が #401 の差分の扱い（入れる・捨てる）を決める必要がある。#398（applySorting の共有化）とも、step4 着手時に git log/status で重なりを確認する。

## 5. 推奨

**A（行単位の窓）＋カードの再利用キャッシュ。kill-switch は既定 OFF、影モードから段階的に入れる。**

理由:
- 913冊の並べ替えで目標（≤100ms・固まる≤50ms）に届く見込みが一番大きい。DOM 側の費用（約125ms）がほぼ消え、残りは JS の約40ms だけ。
- 3000冊のスクロールのカクつきを解消する（試作 4件 対 今 65〜80件）。
- D（段階描画）は3000冊のスクロールを直せない。C は契約・白抜け・戻るでの飛び先に弱い。B は cv の既知の罠を抱えたまま。

残るリスク:
- コンポジタ側の白抜けは、JS からは測れない → 実機の録画で確かめる。
- ページ内検索・印刷の範囲が狭まる → ハヘロ決裁1。
