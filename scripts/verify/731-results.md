# 731-results：publish-article-generator.test.js:110（O(n^2)劣化ガードの主テスト）がCIで5000msの時間切れになる揺れ

イシュー#731（bookshelf-3.1）。基準は origin/main 001101c（2026-11-22 07:26）。測ったのは 2026-11-22 07:37〜07:45 JST、手元は16コア。

## §1 原因と根拠

**結論**：主テスト(L110)は、回数で判定するテストなのに、本体で128K/256K/512K/1MB（合計約1.9MB）を同期のまま変換している。手元では約1.5秒、CIでは5秒前後かかる。Vitest 2.1.9 は同期テストを何秒かかっても時間切れにできなかったので、この遅さは見えていなかった。Vitest 5.1.1（ec3bdf4・2026-11-22 05:02 の版上げ）は、テストの終了時に上限を超えていないかを見て落とす。そのため、以前からあった遅さが赤として出るようになった。

根拠：

1. **版の差の実装**
   - 2.1.9：`@vitest/runner` dist/index.js `withTimeout`（L32-50）は `Promise.race([fn(), setTimeout で reject])` だけ。同期の本体が走る間はタイマーが発火できず、終わると race が先に解決する。＝同期テストは時間切れにならない。
   - 5.1.1：`node_modules/vitest/dist/chunks/run.zBhXlcZQ.js` L3359-3368 の `resolve()` が `deadline.exceeded()` を見て落とす（コメントに vitest-dev/vitest#2920）。
   - この事後の判定は `@vitest/runner` 3.2.0 で入った（3.0.0・3.1.0 の dist には無く、3.2.0・3.2.4 には有る。tarball を取り出して「2920」を grep した）。
2. **再現**：6秒 busy-loop する同期テスト1本（既定 timeout 5000ms）を流した。
   - Vitest 2.1.9：`✓ 6001ms`（通る）
   - Vitest 5.1.1：`× 6002ms` `TestTimeoutError: Test timed out in 5000ms.`（落ちる）
3. **CIの履歴**（run画面のHTMLの注記の本文で読んだ・APIは使っていない）：Vitest 5 で完了した run #419〜#432 の14本のうち6本で、単体の注記が `publish-article-generator.test.js#L110 TestTimeoutError: Test timed out in 5000ms` だった。他の単体テストの注記は0件。
   - 赤：#420 dd0ccd9・#421 c0e99c2・#423 eaa470c・#428 014ebea・#430 ef72c7b・#431 6e7ac8d
   - ubuntu-24.04（#420〜#429）と 26.04（#430〜）の両方で起きる＝実行環境の差ではない。
   - #418 6942583（Vitest 2.1.9）は成功。#419 cf0655e（Vitest 5.1.1）は E2E で赤だが、単体の注記は無い（701-results.md L255 で単体は成功）。
4. **Vitest の上乗せは無い**：同じ4サイズを vitest を通さず素の node で変換しても、主テスト単体とほぼ同じ所要になる（§2 表1）。
5. **node の版の差でもない**：CI の node 22（ci.yml L37）は、手元の node 24 よりむしろ約8%速い（§2 表1）。
6. **CIは手元より遅く、並列でさらに伸びる**：手元でも16並列の全体実行では主テストが 2632ms まで伸びた（単体では約1450ms）。CIでは 14本中6本が5000msを超えた＝中央値は5秒前後。手元単体の約3.4倍と見積もる（CIの所要そのものは未測定＝step2で入れる notice の注記で読む）。

＝brief の候補のうち、「Vitest 5での挙動の変化（タイマー）」と「テストの入力の規模」が原因。「CIのランナーの負荷」は遅さの倍率を決めているだけ。CIの遅さは以前からあり、Vitest 5 で見えるようになった。
