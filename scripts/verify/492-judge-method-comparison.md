# #492 step3: 判定方式A/B/Cの比較と推奨（実装しない・tp）

前提データ（step1・`492-gpu-breakdown.md`）:
- GPU・描画構成はCI/ローカルで完全一致（headless shell + SwiftShaderソフトウェア描画）。
  実機差は hardwareConcurrency(vCPU): CI=4 / ローカル=16 のみ。
- js/layout/paintの内訳比較で、CIで描画・ラスタだけが特異的に重くなる形跡は無い。
- ②の見立て（CIはソフトウェア描画で描画部分が少ないvCPUで重くなる）は前半・後半とも**外れ**。
- A/Aの揺れ（同じcommit同士、交互計測の中央値比）: ローカル order1.075/direction1.009/drag1.049、
  CI order1.004/direction0.978（CIのdragは未取得）。合計5組の範囲は **0.978〜1.075**（最大±7.5%）。

## 比較軸

1. 機械の速さ・描画経路の差への耐性（runごとの揺れを吸収できるか）
2. 退行の検出力（例: drag処理が1.3倍重くなったら確実に赤になるか）
3. CI所要時間の増分
4. #377適合（上限を消さない・警告止めにしない・skipしない）
5. 基準の選び方（origin/mainの1つ前か固定タグか・基準側がすでに退行していた場合の扱い）

## 案A: 同じjob内で基準commitと今を同条件で測り、比で判定

**実装イメージ**: git worktreeで基準commit（既定: `origin/main`の1つ前＝push前のmain HEAD）を
別ディレクトリに展開し、別port（例: PORT+1）で`python3 -m http.server`を起動。同じPlaywright
ページ内で基準URL→今のURLを「基準→今→基準→今…」交互にgoto()し、同じ`measure`/`measureMedian`
ヘルパーで両方を測る。CPUスロットリングのrate計算（#487の動的倍率）は共通化（1回測って両方に適用）。
BUDGET（絶対値・ローカル用）はそのまま残し、追加で「今の中央値 ÷ 基準の中央値 ≤ 比の上限」を判定する。

1. **機械の速さへの耐性**: ◎高い。同じjob・同じ機械で基準と今を測るため、CI機械の絶対速度や
   runごとの変動（vCPU数・ホスト負荷）が両方に同じようにかかり、比はキャンセルされる。今回の
   データ（CIの機械がローカルの約2倍遅い＝T_measured65ms/T_REF32ms）でも、GPU/描画構成が同一
   だった以上、基準・今の両方が同じ条件で測られれば比は安定するはず。
2. **退行の検出力**: ◎高い。drag処理が1.3倍重くなれば比が1.3倍になり、比の上限（1.2〜1.5倍の
   候補）を超えれば確実に赤。絶対値の上限（ローカル用）も並行して効くため二重のガードになる。
3. **CI所要時間の増分**: 元のspec相当（trace/aa等の記録専用計測を除いた、現commitの判定用
   測定のみ）をローカル実測したところ **22.0秒**（trace/aa込みの1-a版は48.0秒だったので、
   記録専用計測の増分が約26秒と判明・step4では記録専用計測は外す前提）。基準側も同条件で
   同程度の測定が必要になるため、**テスト本体の時間はおよそ倍（22秒→40〜50秒程度）** になる
   見込み。ブラウザ起動・webServer起動・レポート生成等の固定オーバーヘッドは1回分で済むため、
   CIのsort-perf単独step全体（現状1分弱〜1分程度と推定）としては **+20〜30秒程度、全体で
   1.5倍前後** になると見積もる。worktree展開自体は`git worktree add`＋浅いcheckout程度で
   数秒以内（npm ciは不要・静的ファイルのみなのでnode_modules共有で足りる）。
4. **#377適合**: ◎適合。絶対値の上限は消さず残す。相対比較を追加するだけで、警告止め・skipは
   行わない。
5. **基準の選び方**: 「origin/mainの1つ前」は運用コストが低い（タグ更新忘れのリスクが無い）が、
   基準自体がすでに退行していた場合、相対比較だけでは追加の退行を見逃しうる（基準が遅ければ
   比が小さく出る）。これは絶対値の上限（ローカル用）を並行して効かせることで一定ガードできる
   ＝完全な解決ではないが#377の多重防御の一部として妥当。固定タグ方式は基準の棚卸しが要る分
   安全だが、タグ更新の運用（誰がいつ更新するか）が未決のため、今回は「origin/mainの1つ前」を
   既定にし、固定タグは将来の改善候補として残す。

   **比の上限の候補**: A/Aの揺れ（5組・0.978〜1.075、最大±7.5%）から、安全マージンを持たせて
   **1.3倍**を推奨値とする。理由: 最大揺れ(7.5%)の約4倍のマージンがあり、A/Aでは赤にならない
   （実測5組のいずれも1.3未満）。かつ、依頼に出ていた1.3倍の意図的な退行例は確実に拾える
   （1.3倍の境界ちょうどなので、実際の運用では1.3倍をわずかに超える劣化を見逃す可能性はある
   ため、1.25倍程度まで絞れないかはstep4の本番同等A/A検証で詰める）。サンプル数が5組と少ない
   （②承認noteの指摘通り、近似のA/Aに基づく暫定値）ため、**step4の実装時に、基準commitを実際
   にworktreeで展開した本来のA/A（基準==基準の比較）をローカルで追加実行し、この1.3倍が
   A/Aの実測揺れに対して十分なマージンを持つか確かめ直す**（②承認済み方針）。

## 案B: 描画を含む基準操作で倍率を合わせ直す（#487の方式を広げる）

**実装イメージ**: #487の「DOMに依存しない計算」の基準操作に加え、軽いDOM描画を伴う基準操作
（例: 要素の再描画や簡易レイアウトのループ）を追加し、CPUスロットリング倍率をJS基準だけでなく
描画コストも加味して決め直す。

1. **機械の速さへの耐性**: △中。そもそも#487は「CIが遅いのは描画が原因では」という仮説の対策
   だったが、step1のデータで**描画（js/layout/paint比率）はCIとローカルでほぼ同水準**と判明
   した。描画を含む基準操作を追加しても、補正すべき対象（CI特有の描画遅延）自体が存在しないため、
   既存のJS基準操作だけの方式と比べて改善効果は小さいと見込まれる。
2. **退行の検出力**: △低〜中。倍率の精度を上げるだけで、「退行を比で検出する」仕組みではない。
   drag処理が1.3倍重くなっても、スロットリング倍率はdrag処理とは無関係な基準操作で決まるため、
   依然としてBUDGET（絶対値・固定）での判定に依存する。runごとの機械差の影響を減らせても、
   #476/#487で実際に起きた「runごとに上限超過する操作が変わる」問題（機械の遅さの変動）への
   対策止まりで、A案のような「今と基準の比較」という根本対策にはならない。
3. **CI所要時間の増分**: 小さい（基準操作をもう1種類測るだけ、数秒程度）。
4. **#377適合**: 適合するが効果が薄い。
5. **基準の選び方**: 関係ない（commit比較ではないため）。

→ **見立てが外れた（描画がCI特有に重くない）ことがstep1で判明した以上、案Bで追加的に補正できる
差はほとんど無いと判断する**。

## 案C: CIの描画条件をローカルに近づける

**実装イメージ**: GPUを模す・ソフトウェア描画の条件をCIとローカルでそろえる（例:
`--use-gl=swiftshader`等の明示指定をローカル側にも入れる、等）。

1. 見立てが外れたため前提（CI特有の描画条件の差）が存在しない。GPU構成（SwiftShader・
   gpu_compositing/rasterization/webgl featureStatus）は既にCIとローカルで**完全一致**している。
   唯一の実機差であるvCPU数（CI=4/ローカル=16）はGitHub Actionsランナーのハードウェア仕様であり、
   ワークフロー側の設定変更では変えられない（より大きいランナーを使う選択肢はあるが、コスト・
   運用面で別次元の判断が必要・本イシューの範囲外）。
2. → **非現実的・不採用**。見立てが当たっていた場合にのみ検討する案だったため、今回のデータでは
   選択肢から外れる。

## 推奨: 案A

根拠（数値付き）:
1. step1のデータで、CIが遅い原因は「機械全体の速度差（vCPU起因、CI=4/ローカル=16）」であり、
   「描画が質的に重い」のではないと判明した（js/layout/paint内訳がCI/ローカルでほぼ同水準。
   direction: paintはCI14-15ms vs ローカル20ms＝CIの方が小さい。drag: paintはCI6-7ms vs
   ローカル5ms＝ほぼ同等）。これは案Aの前提（機械の速さに左右されず、同条件での相対比較なら
   退行を拾える）に直接合致し、逆に案B/Cの前提（CI特有の描画遅延がある）を否定するデータに
   なっている。
2. A/Aの揺れは実測5組で0.978〜1.075（最大±7.5%）と小さく、1.3倍程度の比の上限なら安定して
   緑を保ちつつ、意図的な退行（1.3倍以上の劣化）を確実に拾える。
3. CI所要時間の増分は実測ベースで見積もり可能（元のspec相当22.0秒→基準側追加でテスト本体は
   約2倍、sort-perf単独step全体では+20〜30秒・1.5倍前後）であり、依頼の「CIの所要時間が
   どれだけ増えるかも見積もる」に数値で応えられる。
4. #377（上限を消さない・警告止めにしない・skipしない）に適合（絶対値の上限をローカル用に残し、
   相対比較を追加するだけ）。
