# #612 step1：一括保存で変わっていないファイルも送る件の調査と、案の比較（2026-11-14 13:34〜）

## 0. 最初に：今の照合は、2回目以降の保存では効いていない（再現した）

2台（A・B）が同じハブに保存する場面を、テストで通して確かめた。5件とも想定どおりの結果になった。

- テスト：`tests/unit/zz-probe-612-two-devices.test.js`（未 commit・今の挙動をそのまま確かめるもの）。
- 通した経路：`BookshelfStorage.syncBatch` → `HubStorageAdapter`（js/hub-adapter.js）→ fetch → **本物のハブの処理**（cf-worker/asayake-hub.js の fetch ハンドラ）→ R2 の模擬。
- 通していない所：アプリの画面からの操作（E2E）と、本番の R2。

| 場面 | 結果 |
|---|---|
| 対照：Bが読んだ直後の最初の保存（Aが先に短文メモを保存していた） | Bは `HubRemoteChangedError` で止まる。Aの短文メモは残る＝照合は効く |
| **本命：Bが1回保存した後の、2回目の保存**（Bは設定だけ変えた・短文メモは変えていない） | **エラーも 412 も出ずに成功し、Aの短文メモが保存先から消えた** |
| #616 の交互保存を2回目以降で（Bは別の本に短文メモを書いた） | 成功し、notes.json はBの本2だけになった。Aの本1は消えた |
| 何も変えずに保存（2ファイル） | R2 に2回書いた（同じ中身の書き直し）。保存の前に HEAD を2回送った |
| 本文なしの照合専用エントリ（op:'verify'）を今のハブに送る | ETag が合えば 200 で何も書かない。合わなければ 412。ifMatch が無ければ素通り |

本命の場面で実際に送られた中身：Bは notes.json に `ifMatch:"e5"` を付けた。`e5` は**Aが書いた後の版**の ETag だった。

- 原因：一括保存が成功すると、アプリは覚えていた ETag を全部捨てる（js/hub-adapter.js:281）。次の保存では、各ファイルを HEAD して「今の」ETag を取り、それを ifMatch にする（:247-262）。だから照合は必ず通る。
- 結果：Bの手元にある古い中身（Bが変えていないファイルも含む）で、保存先を丸ごと上書きする。
- #616 で出るようになった3択は、「読んだ直後の最初の保存」でしか働かない。
- 分からないこと：タブに戻った時などに、アプリが保存先を読み直す仕組みが別にあるかは確かめていない。あれば、消える場面は狭くなる。

## 4. 案の比較

**②が足した解消条件：別々の項目を変えた2台の交互保存で、3択が出ないこと。**
#616 の実測の場面（別々の本の短文メモ）は、2台とも同じ notes.json を変えている。だから**件数を減らすだけでは満たせない。同じファイルの中を項目ごとに合わせる処理が要る**（どの案でも同じ）。

どの案にも共通で要るもの：

- (K) ハブが、書いた後の ETag を成功の応答で返す。アプリは ETag を捨てずに持ち続ける。これで2回目以降も「自分が最後に読んだ・書いた版」と照合できる（§0 の穴を塞ぐ）。応答に本文が増えるだけなので、古いアプリはそのまま動く。古いハブに新しいアプリがつながった時は、今までどおり捨てる。
  - ハブを触らない代わりの手：書く前に HEAD ではなく GET して、覚えている中身と比べる。変えるファイルごとに本文を1回余分に取る。
- (F) library.json の日時は、本の一覧が同じなら据え置く。
- (M) 同じファイルを相手も変えていた時、項目ごとに合わせる（自分の前の版・自分の今の版・相手の版の3つを比べる）。合わせられない時だけ3択。まず notes.json（本ごと）。合わせた結果は手元の状態にも入れる（入れないと、次の保存で相手の分を消してしまう）。

| | 案1：変えていないファイルは照合だけ送る | 案2：整合が要る組だけ常に送る | 案3改（推奨）：変えたファイルだけ送る |
|---|---|---|---|
| 整合の安全性（今と比べて） | 最も厳しい。変えていないファイルが他で変わっても 412 で止まる | 今と同じ穴が残る（組の中の変えていないファイルを古い中身で上書きする） | 変えていないファイルは送らないので、上書きしない。他で変わっても気づかない |
| 3択の出方（新しい解消条件） | **今より増える**。別のファイルを変えただけでも毎回止まる。止めずに取り込む形にすると、全種類のファイルで取り込みの処理が要る | 組の中では出る | 別のファイルなら出ない。同じファイルは (M) で合わせる |
| ハブ改修 | 要る（照合専用エントリ＋K） | 要らない（K を入れるなら要る） | K だけ（小さい・互換） |
| 件数の削減 | 本文つきは変えた分だけ。送る件数と R2 の読みは減らない | 1〜4件 | 最大（変えた分だけ） |
| 既存のアプリとの互換 | 古いハブでも偶然通る（§0 の5件目）が、正式な仕様にする作業が要る | 影響なし | 影響なし |

**推奨：案3改（変えたファイルだけ送る＋K＋F＋M）。**

- 計画時の推奨候補は案1だった。変えた理由は2つ。
  1. 案1の照合は、新しい解消条件と逆に働く（別のファイルを変えただけで止まる）。
  2. 「変えていないファイルの照合」は、今も最初の保存でしか働いていない。2回目以降はむしろ上書きしている（§0）。案3改はその上書きをやめるので、今より安全になる。
- 案3改で残ること：自分が変えていないファイルを相手が変えても、読み直すまで手元は古いまま。ファイルをまたぐ食い違いが起きうる（例：Aが本を消し、古い画面のBがその本に短文メモを書くと、本の無い短文メモが残る）。データは消えない。読み込み側がこれを問題なく扱えるかは未確認＝step2 で確かめる。
- 案2は、§0 の穴が残るので採らない。

## 5. ハヘロに上げる必要があるかの材料

- 利用者から見て変わること：
  1. 2台を交互に使っても、別々の本の短文メモなら3択が出ず、両方残る。
  2. 2回目以降の保存で、相手の変更が黙って消えていたのが消えなくなる。その代わり、同じ項目を2台で変えた時は3択が出るようになる（今は後から保存した方が黙って勝つ）。
- どちらも、#616（ADR-159）で②が決めた方向の延長。3択の文言と並びは変えない。**上げる必要は薄いと見る。**
- 上げるなら1点だけ：「別々の本の短文メモは自動で両方残し、3択は同じ項目がぶつかった時だけにする」でよいか。

## 6. 計画への影響（②に決めてほしいこと）

- 推奨どおりなら、step2 の中身が増える：K（ハブの応答）・変えたファイルだけ送る・F・M（notes.json）・2台の交互保存の E2E。M は手元の状態への取り込みを含み、一番難しい。step2 を「K＋送る件数＋F」と「M」の2つに分け、間に確認を入れる方が安全と見る。
- step3 の deploy は、K があるので残る。
- step4 の合格条件に足すもの：ハブで、別々の本の短文メモの交互保存で3択が出ず両方残ること。同じ本なら3択が出ること。
- GitHub のまとめ保存（#616 で照合が入った）は範囲外のまま。ただし M の合わせ方は、ハブと GitHub で1か所に置く形にしたい（ADR-159 の「判定は1か所」に合わせる）。
