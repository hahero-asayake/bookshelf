## GitHub は「存在しないファイルの削除」をエラーにする

- 公式ドキュメント（<https://docs.github.com/en/rest/git/trees> の "Create a tree"）に次の記載がある。
  - 「Returns an error if you try to delete a file that does not exist.」
  - `tree[].sha`: 「If the value is null then the file will be deleted.」
- 返る状態コードと文言は同ページに個別の記載が無い（一覧にあるのは 201・403・404・409・422）。実際の API は叩いていない＝**コードは未確認**。模擬は 422 を仮に返している。
- `js/github-adapter.js:329-331`（commitBatch・sha:null を積むのは330行）は、存在を確かめずに削除（sha:null）を積む。まとめ保存に「もう無いファイルの削除」が1件でも混ざると、その保存（1 commit）が丸ごと失敗する。
- 他の経路は無いファイルの削除を成功として扱う: ハブのまとめ保存は事前に外す（`js/hub-adapter.js` の `_resolveBatchEntry`）、GitHub の単発削除は 404 を成功扱い（`js/github-adapter.js:510`）、ローカルは NotFound を無視（`js/local-fs-adapter.js:122-130`）。

## 直し方の比較

前提になる事実:

- 通常の保存は、書き込みを1回のまとめ保存にして出す（ハブ=1リクエスト・GitHub=1 commit・ローカル=1件ずつ。`js/bookshelf.js:3477-3676`・`js/storage.js:373-406`）。まとめ保存は削除も載せられる。
- slug は空いている一番小さい番号で付く（`_generateDefaultSlug`・`js/bookshelf.js:4961-4966`）。`bookshelf1` を消して新しく作ると、また `bookshelf1` になる＝**同じ名前での作り直しは普通に起きる**。

| 比較軸 | 案A: 消すファイルを覚えておき、通常の保存に削除として載せる | 案B: 分岐を外し、その場で1ファイルずつ消す | 案C: 保存のたびに保存先の一覧と突き合わせ、一覧に無い本棚ファイルを消す |
|---|---|---|---|
| bookshelf-manager に保存先の分岐が残らないか | 残らない（manager は保存先に触らない） | 「保存先に繋がっているか」の判定が残る | 残らない |
| 通信失敗・未接続の時、後で消えるか | **消える**（成功するまで覚えている） | **消えない**（覚えていないので残り続ける） | 消える（次の保存でまた突き合わせる） |
| 他の端末が作ったファイルを誤って消さないか | 消さない（自分が消した本棚の分だけ） | 消さない | **消しうる**。古い状態の端末が保存すると、他の端末が作った本棚のファイルまで消す（GitHub のまとめ保存とローカルには、ファイルごとの衝突検知が無い） |
| 同じ名前で作り直した本棚・読み込み直しで戻った本棚 | 保存の時点で一覧にある slug は消さない、という決まりで守る（必須の手当て） | 削除→保存の順が保たれる限り問題なし | 一覧にあるので消さない |
| 存在しないファイルの削除で保存全体が失敗しないか | **GitHub は手当てが必須**（下記） | しない（単発削除は 404 を成功扱い） | しない（一覧にあるものだけ消す） |

### 推奨: 案A

- 失敗しても後で必ず消える、他の端末のファイルを消さない、GitHub の commit が増えない、の3つを同時に満たすのは案Aだけ。
- 案Bは変更が小さいが、通信が切れている間に消した本棚のファイルが残り続ける＝今回直したい「消したはずのデータが残る」が形を変えて残る。
- 案Cは過去の分まで掃除できるが、他の端末が作った本棚のファイルを消しうる。データを失う向きの危険なので採らない。

案Aで必須にする手当て:

1. **GitHub のまとめ保存で、土台に無いファイルの削除を外す**（`GitHubAdapter.commitBatch`）。ハブの `_resolveBatchEntry` と同じ考え方。これが無いと、もう無いファイルの削除が1件混ざっただけで、以後の保存が毎回失敗する。保存先ごとの差なので adapter の中に置く。
2. **保存の時点で一覧にある slug は消さない**（同じ名前で作り直した・読み込み直しで戻った本棚を守る）。該当する分は「消す対象」から外す。
3. 消す対象は端末の中に覚え、再読込をまたいでも残す。保存が成功したら消す。

### 失敗した時の扱い（決めたい点）

- 推奨: **削除だけの知らせは足さない。保存の失敗と同じ扱いにし、次の保存で自動的に再試行する**。削除は保存と同じ1回に乗るので、失敗すれば保存ごと失敗する。消す対象は成功するまで覚えている。
- 注意（コードを読んで分かったこと・画面では未確認）: **今の「保存の失敗」の見え方は弱い**。
  - 書き込みの失敗は保存処理の中で握られ、外へ出ない（`js/bookshelf.js:3663-3676`）。呼ぶのは `updateSyncStatus('reconnect')` だけで、これは設定画面の同期欄の表示を書き換えるもの（`js/bookshelf.js:3747-3776`。文言は「（要再接続）」「『フォルダを選ぶ』を押して…」で、ハブ・GitHub でも同じ文言）。
  - 上部に出る「…への保存に失敗しました」（`js/bookshelf.js:2869-2888`）は、例外が保存処理の外へ出た時だけ。通常の書き込み失敗では出ない見込み。
  - 未同期の印（`virtualBookshelf_pendingSync`）は残るので、次の保存では送り直される。
- つまり案Aにすると「削除の失敗＝保存の失敗」になり、後で必ず消えるが、失敗した瞬間に利用者が気づけるかは今の保存失敗の見せ方しだい。step3 で「失敗→次の保存で消える」の E2E を書く時に、失敗時に画面へ何が出るかを実測して報告する。
- 保存の失敗そのものを利用者に分かる形で知らせる改善は、本棚ファイルに限らない話なので、このイシューには入れず別イシューにするのがよい（②の判断を仰ぐ点）。

### ローカル：未接続の間に削除→繋ぎ直す（実測）

- 手順: フォルダに繋いで本棚を作る → 再読込を「権限待ち（要再接続）」にする → 本棚を削除 → 設定から「フォルダを選ぶ」で繋ぎ直す。
- 結果: 削除待ちには積まれていた（`["bookshelf1"]`）。しかし**繋ぎ直すと、削除した本棚がフォルダの内容から戻ってきた**（アプリ内・フォルダの一覧とも本棚あり）。ファイルも残る（一覧にある本棚なので、作り直しと同じ扱いで消さない）＝本棚とファイルは食い違わない。
- 原因（既存の挙動）: 未接続の間は保存の予約が立たない（`saveUserData` は `_isSyncReady()` の時だけ `_scheduleSync` → `virtualBookshelf_pendingSync` が立たない・`js/bookshelf.js:2826-2829`）。繋ぎ直しの読み込みは「未同期のローカル編集」が無いものとして、フォルダの内容で上書きする（`_applyLoadedState`・`js/bookshelf.js:3253-3258`）。本棚の削除に限らず、未接続の間の編集すべてが戻る。
- ②の期待「繋ぎ直すとファイルが消える」とは違う。削除そのものが戻るのが原因で、このイシューの範囲（保存先に残るファイル）の外。未接続の間の編集を繋ぎ直しで失う件として、別イシューにするのがよい。
